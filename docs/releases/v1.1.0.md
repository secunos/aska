# Aska v1.1.0 — release record

**Tag:** `v1.1.0` (annotated, by the release owner `secunos`; the tag commit is the one built, `5c0813f`). **Built:** 8 October 2026, 19:21 UTC. **Status:** feature release on top of 1.0.1 — the 1.1 plan (`docs/Aska_1.1_Plan_v0.3.md`) steps 1–6. **Not independently audited and not legally reviewed** — see `SECURITY.md`, the User Guide §1 and §9; the owner decided on 7 October 2026 that neither review is planned.

## What changed since 1.0.1

1. **Hardening (step 1).** On the receiving-key path the clients' closing line no longer differs after a distress open (it was decided after the open, which destroys the seed — a tell against a decoy open, found in the 7 October specification re-issue). Command-line `--ttl` accepts only the six TTLs the cover traffic imitates; `receive --class` is honoured for words and Shares; the CLI profile commands check the path like the GUI (regular file, exact size, no symlink following); circle client-auth keys are cleared at `Session::close()`; the profile passphrase is normalised without a growing `String`; the Key Card decoder is strict per Block Format §7.3 (pre-review B-7) in Rust and the Python reference; the relay wipes expired labels, spent challenges, digests and refused Block bodies in place; the installer configures the RAM-only journal before the relay's first start and checks it.
2. **Command-line input in locked memory (step 2, pre-review C-10).** Every line typed at a prompt — passphrases, Key Cards, Shares, seeds, the note — is read one byte at a time into fixed-capacity locked buffers; nothing goes through the standard 8 KiB input buffers. A new gate (`scripts/cli-input-unbuffered.sh`) traces the reads in CI. The GUI memory gate now also sets and enters a passphrase and looks for it and for the 24 words afterwards (C-17).
3. **Receiving seeds in the encrypted profile (step 3, RM-09).** A profile can hold up to eight receiving-key seeds (TLV `0x10`, profile files only; a 1.0.x client ignores it). CLI: `profile add-seed --new | (from 24 words)`, `profile remove-seed`, `profile open` lists keys by their twelve-character check, `key receive --stored`, `receive --receiving-seed` accepts the words, a stored key's check or an empty line for the only stored key. GUI: Receiving-key page lists stored keys with Store/Remove; Receive page offers "Use a stored key". The file stays one 4 KiB Block, rewritten in place.
4. **Screen capture on KDE Plasma (step 4).** Finding: no Wayland protocol lets an application hide its own window from capture. Plasma 6.6 added *Hide from Screencast* (6.7: *Hide from Screenshots and Screen Recordings*, also as a window rule) as a user action; on Plasma 6.6+ the doctor and the View page point at it and say Aska cannot turn it on itself.
5. **Camera in-process (step 5, C-04; decision D-22).** New crate `aska-scan`: Video4Linux2 capture written against the kernel's stable interface with `libc` only, a pure-Rust QR decoder (`rqrr`), frames wiped and camera buffers blanked. The graphical client's *Scan with camera…* opens a viewfinder; the command-line `scan` reads the camera in-process; the `zbarcam` helper remains the fallback (cameras offering only MJPEG; `--scan-helper`). **The live camera path has not been run on real hardware** — see Deviations.
6. **Read-only note viewer (step 6, C-02).** The View page draws the note from a locked buffer one word at a time instead of putting it into a GTK label; nothing is selectable or copyable and accessibility tools see an image. Memory gate while a note is on screen: two copies (the Session's and the viewer's locked buffers, both wiped on close), down from five.

**Not in 1.1:** bridges for the session (RM-08, dropped by the owner on 8 October; it stays on the roadmap). The Send editor is still a GTK text view (C-02 remains for input).

**Compatibility.** Notes, Key Cards, Shares, Receiving Keys and profiles made by 1.0.x work with 1.1.0 and the other way round (a 1.1 profile opens in 1.0.x without its stored seeds). The wire protocol is unchanged (ADP/1); relay operators need not upgrade.

## Deviations and known issues

1. **Live camera path unvalidated (T-31).** No machine available to the project has a webcam, so `aska-scan`'s capture path (device open, format negotiation, streaming) and the viewfinder dialog have run only against the no-device case. The decoder and the pixel-format conversions are tested on generated QR codes in synthetic frames; the V4L2 structure layouts and request numbers are asserted against the kernel headers. The first report from a machine with a camera is the validation; the `zbarcam` helper remains available meanwhile.
2. **Two informational advisories** on the dependency `lru 0.12.5` (via `rqrr`): RUSTSEC-2026-0002 (an aliasing issue in `IterMut`, which `rqrr` never calls) and RUSTSEC-2026-0253 (a use-after-free reachable only with unwinding panics and a key type whose `Drop` can panic; Aska builds with `panic = "abort"` and the keys are plain integers). Both accepted; `cargo deny` and `cargo audit` pass.
3. **Not built in the release container**; **no Rekor entry**; **reviews not planned** — as for 1.0.x (D-19, D-20, D-21).
4. **Design documents:** re-issued at the tag — Decision Record v0.5, Client Design v0.7, Block Format draft 0.7, ADP/1 draft 0.4 — and included in the tagged source.

# Aska v1.2.3 — release record

**Tag:** `v1.2.3` (annotated, by the release owner `secunos`; the tag commit is the one built, `95aad7c`). **Built:** 2026-10-30 19:25 UTC (second build; the first, from `0bfd7ab`, was discarded before the tag was pushed — see "Deviations and known issues"). **Status:** patch release on top of 1.2.2 — **brand 3.0** (the *ASKA Brand Guidelines 3.0*, decided 30 October 2026, supersede brand 2.0 shipped in 1.2.2). **No change to Aska's own code, behaviour, format, protocol, rule or gate; two dependency patch updates** (item 7) for advisories published after 1.2.2. Not independently audited and not legally reviewed, as every release before it.

## What changed since 1.2.2

1. **The icon.** `org.aska.Aska` is the **Perforerad mark** — a perforated plate of round holes in staggered rows that shrink toward the upper right — in ink on a **signal yellow** (`#F2C230`) tile; the `hicolor` theme ships PNGs 16–512 (a simplified small master at 16–24 px, a mid master at 32–48 px), the scalable SVG and a symbolic SVG of seven holes that GTK recolours. `install.sh` and the User Guide's removal command are unchanged (same file names).
2. **The palette.** Black and white stay (window `#FFFFFF`/`#0B0B0B`, surface `#F5F5F5`/`#161616`, text `#111111`/`#F2F2F2`, muted `#666666`/`#9A9A9A`); the one brand colour is now signal yellow, used as a fill and never as text on a light ground or for a state. The main button is **ink with a yellow label** in the light style and **yellow with an ink label** in the dark style; the focus ring follows the accent. Warnings are **orange** (`#8A4B00` on `#FDF1E4` light, `#FFB15C` on `#24180C` dark) so that no warning can be mistaken for the brand colour. Every text colour passes 4.5:1. The sheets (`crates/aska-gui/brand/aska.css`, `aska-dark.css`) make every control a **2 px** rectangle and cards **4 px** (they were 4 and 8 in 1.2.2).
3. **The stacked logo on Home.** The Home screen shows the kit's primary lockup: the mark with the name **ASKA** (Archivo Expanded SemiBold capitals as outlines) **below** it, the mark 72 px tall, the block 120 px, in black on the light style and as the yellow mark with the white name on the dark style; no slogan, as since 1.2.2. The two images share one geometry, so switching the colour scheme changes nothing in the layout. Because the stacked block is 36 px taller than the horizontal lockup's 84 px block, the four Home buttons sit 36 px lower than in 1.2.0–1.2.2; the coordinate-driven GUI gates (`scripts/memory-gate-gui.sh`, `no-file-writes-gui.sh`, `memory-gate-paper.sh`) click the new rows (Send y 260, Receive 311, Paper 441 at the gates' window sizes).
4. **Names.** Unchanged since 1.2.2: the window title and the launcher entry are **ASKA**; the command, the file names and the application id stay lowercase (`aska`, `aska-gui`, `org.aska.Aska`). The CLI headline, the locales and the desktop entry's description are unchanged.
5. **Banners and the Tor state.** Unchanged in behaviour and wording; only the warning colour moved from amber-yellow to orange (item 2).
6. **The repository.** README lockup (the horizontal 3.0 lockup, black on light and signal on dark), `docs/brand/README.md` rewritten for 3.0, SECURITY.md status, User Guide header and §3.4 (icon description, mark above the name). The 2.0 lockup files are removed; the kit's `aska-tokens.json` 3.0 is the colour source of truth.

7. **Two dependencies, for advisories published after 1.2.2.** The tag-push CI run of update 43 failed in `cargo deny`: **RUSTSEC-2026-0385** — `ctutils` 0.4.2 (a transitive dependency of `ml-kem`, through `hybrid-array` and `module-lattice`) generated mask values and 32-bit `u128` comparisons with branches in code meant to be constant-time, so a secret could in principle leak through a timing side channel; fixed in 0.4.4, verified by the maintainers with BINSEC — and **RUSTSEC-2026-0386** — `tokio` 1.53.1's safe `AsyncFd` constructors violate I/O safety (unsound; Aska does not use `AsyncFd`, so it was not affected in practice). `cargo update -p ctutils -p tokio` moved `ctutils` 0.4.2 → **0.4.7** and `tokio` 1.53.1 → **1.54.1**; nothing else in `Cargo.lock` changed, the crate count stays 171, both compile on the pinned `rustc 1.95.0` (`rust-version` 1.87 and 1.85). The full workspace test suite, with the ML-KEM and X25519 known-answer vectors, passes unchanged, and `cargo deny check` is green (advisories, bans, licenses, sources). The ten pre-existing duplicate-version warnings (`block-buffer`, `digest`, `sha3`, `syn`, … — the RustCrypto 0.10/0.11 split that `ml-kem` 0.3 requires, and the GTK/clap macro stacks) are unchanged and remain warnings by policy.

Nothing is read from disk at run time for any of this: the colour sheets and the lockup images are compiled into the binary. No font is installed or needed. `aska --version` → 1.2.3.

**Compatibility.** Identical to 1.2.0, 1.2.1 and 1.2.2 in everything but appearance and the two dependency versions; notes, keys, Receiving Keys, pad pages, cards and profiles are unaffected; the relay is unchanged (operators need not upgrade; `aska-drop` 1.2.3 is a rebuild).

## Deviations and known issues

Those of 1.2.0 carry unchanged (camera path and PHYSICAL source unvalidated on hardware; paper rules stated, not enforced; printing leaves records; live CUPS path not exercised; two `lru` advisories (unmaintained, no fix available; `rqrr`'s dependency); no container build, no Rekor entry, no reviews). Decision Record v0.7 and Client Design v0.9 (20 October) describe brand 2.0 — the horizontal lockup, 4/8 px radii, the Fade icon; to be folded at their next re-issue, with the mobile design's approval (DC-05 §5.6 likewise). **First signed build discarded (30 October, before the tag was pushed):** the developer's verification of the first signed files found `docs/RELAY_OPERATOR_GUIDE.md` inside both tarballs differing from the file at the tagged commit by one digit — the tarball's copy referred to the Dead Drop Protocol draft 0.4, the committed file to draft 0.3 (a stale reference left over from 1.1.0, when the specification was re-issued as 0.4). Everything else in the tarballs was byte-identical to the repository. `release.sh` refuses a dirty tree, so the owner's working copy differed from the commit without `git status` reporting it; the cause was not established at the time of writing (the owner's diagnostics of the working copy are pending; if they show anything beyond a stale stat entry, it will be recorded in the publication paragraph). The reference was corrected in the repository (to 0.4), the local tag was deleted and recreated on the corrected commit, and the release was rebuilt and re-signed; the values in this record are those of the second build. The developer's `VENDOR-HASH` (`52ecc94a…`, computed with cargo 1.97 in the developer's container) differs from the owner's and CI's (`7b813a01…`, cargo 1.95, the pinned toolchain) with an identical `Cargo.lock`: the hash is taken over `cargo vendor`'s output, which differs between cargo versions; the pinned toolchain's value is the one of record, and CI's agreement with the owner's is the check. **CI red on `main` after the record was pushed (30 October, before the tag push):** the `test` job failed at `scripts/timing-parity.sh` — `seed_matching_time_does_not_depend_on_a_match` reported p = 0.0011 (medians 2.80 ms hit and 2.80 ms miss) against the gate's p ≥ 0.01, on a commit that changed two documentation files. The developer re-ran the test twenty times in its container with the released `ctutils` 0.4.7 (smallest p 0.151) and fifteen times with the previous 0.4.2 (smallest p 0.083): no hit/miss difference with either version, the p-values spread as they should when there is nothing to find. The failure is the one-in-a-hundred chance failure that a significance test at the 1 % level has by construction, amplified by a shared runner's drift; it says nothing about the release, whose binaries do not contain the tests and whose matching code is unchanged since 1.2.0. Fixed on `main` after the tag, in the gate only: a measurement that fails is repeated once and the gate fails only when both measurements fail (false alarm 0.01 % per run; a real effect gives p ≈ 0 every time and still fails), with a sanity test of the rule. The tag is not moved. The developer's build of this release was made in a freshly created container with `rustc 1.97.0` (stable), because the pinned `1.95.0` toolchain could not be downloaded there; the owner's release build uses the pinned toolchain as before, and the reproducibility claim rests on it, not on the developer's build. The guidelines' typography (Archivo Expanded for display, JetBrains Mono for fingerprints) is not applied inside the client, which uses the platform's interface and monospace fonts, as the guidelines prescribe for the `ui` and `mono` roles; the brand face appears only in the outlined logo files.

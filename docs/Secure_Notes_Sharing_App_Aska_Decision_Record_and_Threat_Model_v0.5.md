# Part I — Decision Record

## 1. Purpose

This document closes the research phase and opens the design phase. Part I records the decisions taken on 25 September 2026 that fix the shape of version 1, with the alternatives considered and the conditions under which each should be revisited, and the two decisions of 30 September 2026 (D-16, D-17) that were taken during implementation and folded in with version 0.3. Version 0.4 adds the four decisions taken on the way to the first public release (D-18…D-21, 5–7 October 2026) and records honestly which requirements the released software does not meet and why. Version 0.5 adds the one design decision of release 1.1 (D-22, the camera) and records what 1.1.0 changed in the requirement statuses: which pre-review items it resolved, which item it closed as not implementable, and what it leaves open. Part II states the threat model those decisions were made against: what is protected, from whom, and what is explicitly not defended. Part III turns both into numbered requirements that the coming specifications — the Block format, the Dead Drop protocol and the client — must trace to.

## 2. Summary of version 1

> **Version 1 in one paragraph**
>
> A **desktop Linux application** (Tails and Qubes as reference environments) for a **small, trusted circle under high threat**, implementing **Option C with the digital core first**. A note is sealed into a fixed-size, random-looking **Block** using a fresh 256-bit symmetric key with a key-committing AEAD; the Block is posted over **Tor to a self- or friend-hosted onion-only Dead Drop relay** that stores it under a random label until its **time-to-live expires** (default 24 h, maximum 7 days) and keeps no logs or accounts. The **key travels separately**: by default as a QR code or 24 words over a second channel (**no public-key cryptography at all**); optionally encapsulated to a **one-time hybrid post-quantum receiving key (X-Wing)** the receiver published earlier. For coercion resistance the key can be **split 2-of-3 or 3-of-5 among human trustees**, with verification, and reassembled only on the receiver's device. Every Block carries a **decoy slot** and supports a **distress passphrase**. Receivers **download the whole recent bucket** and try their keys locally, so the relay never learns who a Block is for. The client is **native, reproducibly built, amnesic**: nothing is written to disk in plaintext, keys are zeroised after use, there is no history and no identity. The **paper / one-time-pad mode** follows in a later release using the same container. Keys are never reused; there is no audit receipt; cover traffic is modest; the client warns on weak platforms; independent legal review precedes any release beyond the circle (*0.4:* this did not happen — the owner released 1.0.0 publicly without the legal and the independent security review, D-19). The working name of the application is **Aska**.
>
> **Added in 0.3.** The **receiving-key path is part of version 1** (D-17, milestone M5c): a receiver creates a receiving key once, publishes the public `askar1…` Receiving Key by any channel, and the sender seals to it — nothing secret travels and there is no hand-over; the two parties confirm the key's *check* over a second channel (eight characters in 0.3; a twelve-character hash of the public key since the M8 pre-review, see T-27). When the **local network blocks Tor**, Aska does not work around it: it detects the condition where it can, says so, directs the user to the platform's own Tor connection tool, and can use Tor Browser's Tor once that has connected; it never configures Tor and never falls back to a non-Tor path (D-16).
>
> **Added in 0.4.** Version 1 is **released**: Aska 1.0.0 (6 October 2026) and 1.0.1 (7 October 2026, a command-line fix) are published as signed files on a public GitHub repository under a pseudonymous account (D-20). They passed the project's own gates and an **internal** security pre-review, which changed two normative behaviours — every Block now writes its slots under a random permutation of the header indices, so an opened decoy says nothing about whether a real note exists, and the Receiving Key check is a 60-bit hash of the public key — but **no independent security review and no legal review** (D-19). The signed releases were smoke-tested on Debian 13 only; Tails and Qubes remain the reference environments by design but were exercised on development builds only (D-21). The hand-over encodings keep their recognisable prefixes (D-18).
>
> **Added in 0.5.** Release **1.1.0** (7–8 October 2026) changes **no byte of the Block Format or of the wire protocol** and nothing in how the relay treats a 1.0.x client; it is a client and hardening release. A receiver who keeps a long-lived Receiving Key can now **store its seed in the encrypted profile** (RM-09, built) instead of typing 24 words each time — a 1.0.x client opens such a profile without the seeds. QR codes are **read by Aska itself from the camera** through Video4Linux2 with a pure-Rust decoder (D-22), the `zbarcam` helper remaining the fallback; the live camera path has not yet been run against real hardware (T-31). The command-line client reads **every typed line into locked, fixed-capacity memory** (pre-review C-10 resolved), and the graphical client shows a note through **its own read-only viewer** that keeps the text out of the toolkit (C-02 resolved for the View page). The pre-review's C-15, B-7 and the distress-tell finding of the 7 October re-issue are fixed. The "KDE per-window capture flag" of earlier designs turned out to be **not implementable by an application** — no Wayland protocol lets a window exclude itself from capture; Plasma 6.6+ offers it as a *user* action, which the client now points at. **Bridges for the session (RM-08) were dropped from 1.1 by the owner** and stay on the roadmap with no release assigned. The D-19 and D-21 waivers stand: no independent review, no Tails or Qubes validation of a signed build.

Decisions D-01 to D-04 are *gating*: they determine the Block format and cannot be changed later without a format version bump. D-05 to D-22 are *design-scoped*: they can be revisited during design review without breaking compatibility (D-17 changes no byte of the Block layout; it makes a reserved region normative; D-18…D-22 change no byte of the Block layout or of the wire protocol). D-18…D-22 name the requirements they affect at the end of the *Chosen* cell.

## 4. Consequences of the decisions

Taken together the decisions have some consequences worth stating plainly. Version 1 has **no server-side state beyond expiring Blocks, no accounts, and no operator role** — which means there is also no way to recover a lost key, no way to know whether a Block was collected, and no support desk that can help; for the target user these are features. The **default path contains no public-key cryptography**, so the post-quantum question reduces to "is AES/XChaCha with 256-bit keys safe", to which the 2026 answer is yes; the optional X-Wing path is where PQ hybrid cryptography enters and where agility matters most. **Expire-only disposal** means a Block may sit on a relay for up to seven days as noise; that is acceptable because the key is elsewhere and the Block is indistinguishable from decoy traffic. **Desktop first** means the mobile duress/auto-reboot story is deferred; the desktop equivalent is running from Tails or a Qubes disposable, which the client will guide. **No timelock in v1** means the solo-traveller case (Option C doc UC3) requires a human trustee; that is a deliberate trade for avoiding a trusted third party and a non-PQ component.

Two consequences follow from the decisions of 30 September 2026. **With D-17 the hybrid post-quantum path ships in version 1**, so the agility and review burden that §3 placed on "the optional path" is a v1 burden: the X-Wing composition, the `elligator2` crate and the accepted T-28 bias are named items for the external review (OPS-05), and the sender of a receiving-key Block holds nothing to hand over, so the Guarded level (Shares) does not apply to that path — the receiver's protection against coercion there is the short TTL and the fact that the seed is theirs alone. The symmetric default and its "no public-key cryptography" property are unchanged. **With D-16 a network that blocks Tor is an availability failure and nothing more**: the client has no second path, sends nothing outside Tor, and the only thing the local network learns is that Tor was attempted — which the attempt already revealed. The remedy lives in the platform (its Tor connection tool), not in Aska; on a network whose owner forbids Tor the correct response is to use another network, and the client's messages do not suggest otherwise.

The release decisions of October 2026 have consequences that this record states plainly (added in 0.4). **With D-19 two MUSTs and one decision are not met for 1.0.x:** the independent security review (OPS-05) and the legal review (OPS-06, D-13) were to precede any use outside the circle, and the public release is such a use. The requirements keep their text and are marked *waived by the owner for 1.0.x (D-19)*. Users therefore rely on an implementation that only its authors and an internal pre-review have examined (T-29), and on decoy and distress features whose legality nobody has reviewed in any jurisdiction (T-15). The items §3 and §4 had reserved for the external review — the X-Wing composition, the `elligator2` crate, the T-28 sample size — have only the authors' confirmation, and so do the two normative changes the pre-review introduced (the header permutation's draw and the 60-bit check). **With D-20 the trust anchor for software integrity is the release key and the out-of-band fingerprint, and nothing else:** the hosting platform is trusted for nothing, there is no transparency-log entry for 1.0.x (OPS-03 not met), and no independent rebuild has been recorded, so a release signed with a stolen or coerced key would be caught only by users who compare the fingerprint they received out of band (T-18). **With D-21 the reference environments of D-03 are untested on the signed releases.** The User Guide nevertheless recommends Tails "for anything that matters", which is exactly the situation D-21's second revisit trigger names; until Checklist B has been run on a signed release, that recommendation rests on design and on a development-build run, not on a validation (T-30). **With D-18** a hand-over string shows anyone who sees it that it is Aska key material; the 24 words are the form to use where that matters.

Release 1.1 adds consequences of its own (added in 0.5). **With RM-09 built, a receiving seed can be a persistent key.** Until 1.1.0 the client never wrote a seed anywhere; now the user may store up to eight seeds in the encrypted profile, under the profile passphrase and Argon2id, and a 1.0.x client opens such a profile without seeing them. A stored seed is exactly what KEY-07's single-use advice warns against made convenient: every Block encapsulated to it that is still on a relay or was captured opens with it, a Session's distress does not touch the profile file, and the holder can be ordered to open the profile (T-15, T-27 "seed compromise"). The user chooses this explicitly — each store asks the passphrase, a new seed's words are shown once as the paper backup, and the line "this receiving key has been used — create a new one for the next note" is still shown after every open — and the design holds to KEY-09's "except as the user directs". What is missing: neither the User Guide §7.1 nor the clients say in so many words that a stored seed opens every Block still sealed to it; the per-open line is the only reminder (a wording gap recorded against CLI-14). **With D-22 the camera is Aska's own code**, which is both the point and the cost: key material scanned from a QR code now lands in memory Aska wipes rather than in a helper process, but the project ships `unsafe` ioctl and `mmap` code that no independent party has reviewed and that has not been exercised on a real camera (T-29, T-31); until a webcam run is recorded, the in-process path is a design claim, and the helper fallback is the path that has been used. **With RM-08 dropped from 1.1 the D-16 story is complete as released**: there is no bridge configuration anywhere in Aska, the platform's own Tor tool is the only remedy on a blocked network, and §10's boundary needs no "until v1.1" qualifier. **The "KDE capture flag" is closed as impossible, not deferred**: no Wayland protocol lets an application exclude its own window from screen capture; Plasma 6.6+ offers it as a user action, and the client can only say where it is. CLI-08's SHOULD therefore has no platform on which it could be met by the application, and T-09's residual — the note on screen is capturable — is a property of the desktop, not a gap in Aska. **The hardening of 1.1.0 removes two residues** that 0.4 recorded as accepted or deferred — the CLI's buffered input (C-10) and the toolkit's copies of a displayed note (C-02, View page) — and one tell: the closing line after a distress open on the receiving-key path, found by the 7 October re-issue and fixed before any user could have met it in a release. The Send editor is still a GTK text view (C-02 remains for input), and the D-19 and D-21 waivers carry to 1.1.0 by the owner's decision of 7 October 2026.

# Part II — Threat Model

## 5. System context

Version 1 consists of three components and two kinds of out-of-band channel. The **Client** is a native Linux application (with a command-line core) run by senders, receivers and trustees. The **Dead Drop** is a stateless onion-service relay run by a member of the circle. The **Block** is the data format that passes between them. The **key channel** is whatever the sender and receiver use to move the key or its Shares — a QR shown in person, words read over a call, a receiving key published earlier. The **Tor network** carries Blocks between Client and Dead Drop. Nothing else exists: no directory, no account server, no update server (releases are files with published fingerprints — since D-20, minisign-signed files on the release page of the public GitHub repository, with the fingerprint handed out through another channel; the client never contacts the repository), no analytics. On the receiving-key path (D-17) the key channel carries nothing secret: the public Receiving Key may travel over any channel, including a public one, and only its twelve-character *check* (eight characters before the M8 pre-review; T-27) needs a second channel to confirm authenticity. The Client uses the **system Tor** (or Tor Browser's Tor) through a loopback SOCKS port — or, on a detected Whonix Workstation only, the Whonix gateway address 10.152.152.10 — and never configures it (D-16). *Since 1.1.0:* when a QR code is read from a camera, the Client reads the camera device itself (`/dev/video*`, D-22) — a local device, nothing leaves the machine — and the **encrypted profile**, if the user keeps one, may hold receiving seeds as well as the relay list and circle key (RM-09); it stays one class-1 Block on disk, opened only with the profile passphrase.

## 7. Actors and trust assumptions

| Actor | Role | Trusted for | Not trusted for |
|---|---|---|---|
| Sender | Writes and posts a note; hands over key or Shares | Not retaining plaintext or key (enforced by client) | Device integrity at time of writing (see A-6) |

## 10. Explicitly out of scope for version 1

- Protecting a note from a device that is compromised while the note is being written or read (T-09, T-17). The design limits consequences; it does not prevent them.
- Resistance to a global passive adversary performing end-to-end traffic correlation (T-06). Mitigated, not solved; a mixnet transport is a roadmap item.
- Availability guarantees. A relay may be offline; senders may post to two relays; there is no delivery confirmation by design.
- Group messaging, threads, attachments larger than the largest Block class, or any form of conversation history.
- Mobile clients, timelock Shares, threshold decryption, anamorphic encryption and the paper/one-time-pad mode — all roadmap, all designed for in the Block format. (The receiving-key path, deferred to v1.1 at specification level by S-04, is **in** scope since D-17.)
- Legal protection for the *act* of using the system, possessing it, or triggering the distress function; addressed by D-13. (*0.4:* the D-13 review was not done for 1.0.x — D-19; T-15. *0.5:* nor for 1.1.0; not planned.)
- **Working around a network that blocks Tor (D-16, DC-01 §9).** Aska's guidance addresses networks that censor Tor — the environment its users are designed for, and a standard, documented Tor use case. The client does not acquire bridges, does not probe or fingerprint the network it is on, and does not attempt to defeat any particular network's policy. On a network whose owner forbids Tor, such as an employer's, the correct response is to use another network; the client's messages do not suggest otherwise. ~~Session-scoped bridge configuration through the control port, with bridge lines the user obtained through Tor's own distribution channels (option B), is v1.1 and does not change this boundary.~~ *0.5:* option B was dropped from 1.1 by the owner (8 October 2026) and stays on the roadmap as RM-08 with no release assigned; were it ever built it would not change this boundary.
- Enforcing single use of a receiving seed. The format cannot enforce it and the client does not (KEY-07 as revised): the client tells the receiver after each open and the choice is theirs. *0.5:* storing a seed in the encrypted profile (RM-09) is that choice made explicit; the client asks the passphrase for every store and still says after every open that the key has been used (the cost itself is stated here, KEY-07, not yet in the guide — CLI-14).
- **Hiding Aska's own window from screen capture (added in 0.5).** No Wayland protocol lets an application exclude its window from screenshots or recordings, and X11 has no notion of it; where a desktop offers it (KDE Plasma 6.6+, as a user action or window rule) the client points at it and cannot turn it on itself (T-09, CLI-08). Detection of capture (CLI-09) is in scope and partial.
- **Decoding MJPEG camera streams in process (added in 0.5, D-22).** Cameras that offer no raw pixel format are handed to the `zbarcam` helper; a JPEG decoder is not brought into the client for this.

# Part III — Requirements

Requirements use MUST / SHOULD / MAY in the RFC 2119 sense (SHALL = MUST in the requirements imported verbatim from DC-01 and DC-02). Each cites its source decision (D-nn) and the threats (T-nn) it addresses. "Client" means the desktop application and its command-line core; "Relay" means the Dead Drop software.

**Specification-level decision S-04 (revised by D-17).** Block Format draft 0.2 decided S-04 as "X-Wing KEM path deferred to v1.1; v1 clients are symmetric-only and fill the KEM region with random bytes", with two prerequisites (Elligator2 access in the X-Wing implementation; confirmation of ML-KEM ciphertext pseudorandomness under compression). On 30 September 2026 D-17 revised it to: "KEM path as in DC-02 §2, built in v1 (M5c); version-1 clients that do not implement it fill the KEM region with random bytes (unchanged); implementations that do MUST follow DC-02 §2.2 (Block Format §6.5.2) for the X25519 half. No change to the Block layout." Block Format §6.5 and §7.5 (normative since draft 0.4; current draft 0.7, which carries the draft-0.5 check of §7.5.3) are the normative text.

**Block Format and release 1.1.0 (added in 0.5).** Release 1.1.0 changes no byte of the Block layout, the key hierarchy or the encodings. Two implementation facts touch the Block Format's §7.3 (Key Card TLV): (a) **B-7 resolved** — the Key Card decoder is strict as Table 5 of §7.3 requires: the version element first and single, the root, class, TTL and auth elements at most once and with exactly their defined lengths, relay hints repeatable, unknown types skipped, anything else an encoding error — in Rust (`encodings.rs`) and in the Python reference, with four tests; (b) the **profile format** (Client Design, decision C-07) reuses the Key Card TLV and, since 1.1.0, appends `TLV_PROFILE_SEED = 0x10` elements (32-byte receiving seeds, repeatable, at most `MAX_SEEDS` = 8) which a Key Card decoder skips as unknown by rule (a) — so a 1.0.x client opens a 1.1 profile without its seeds, a Key Card never carries 0x10, and the file remains one class-1 Block rewritten in place (RM-09; KEY-09).

# Releasing Aska

Client Design §9 (OPS-02 reproducible builds, OPS-03 signing and transparency, §9.4 how a
member verifies). This is the procedure the release owner follows; `scripts/release.sh`
does the mechanical parts.

## 1. What a release is

A tag `vX.Y.Z[-suffix]` on a commit whose CI is green, and in `dist/release/<tag>/`:

| File | What |
|---|---|
| `aska-gui-X.Y.Z-linux-x86_64.tar.gz` | graphical + command-line client; inside: `bin/aska` (static-pie), `bin/aska-gui` (links the system GTK 4 ≥ 4.14 / libadwaita ≥ 1.5), desktop entry, icon, `install.sh`, `README.txt`, `docs/USER_GUIDE.md`, `docs/RELAY_OPERATOR_GUIDE.md`, `SHA256SUMS`, `SHA256SUMS.minisig` |
| `aska-gui-….tar.gz.minisig` | detached signature over the tarball |
| `aska-drop-X.Y.Z-linux-x86_64` + `.minisig` | the relay, static-pie, for operators |
| `aska-drop-deploy-X.Y.Z.tar.gz` + `.minisig` | `install-debian.sh`, `torrc.aska-drop`, `aska-drop.service` and the Relay Operator Guide, for operators |
| `SHA256SUMS.txt` + `.minisig` | hashes of the downloadable files, signed |
| `aska-release.pub` | the public key (also embedded in the binaries) |
| `RELEASE-NOTES.txt` | commit, toolchain, key id, Rekor entry, verification instructions |

The binaries embed the **public key** and the **tag** (`ASKA_RELEASE_PUBKEY`,
`ASKA_RELEASE_TAG`), nothing else; a binary cannot contain its own hash. `aska verify` hashes
itself, finds `SHA256SUMS` + `SHA256SUMS.minisig` (beside the binary, one directory up, or in
`~/.local/share/aska/` where `install.sh` copies them), checks the signature with the embedded
key and checks that the list names its own hash — all offline. The Rekor entry covers the
tarball signature and is published in the release notes, not embedded.

## 2. The release key (once, and on rotation)

```sh
mkdir -p ~/.minisign
minisign -G -p release/aska-release.pub -s ~/.minisign/aska-release.key -c "Aska release signing key"
```

Choose a strong passphrase; minisign encrypts the secret key with it. Commit the **public**
key (`release/aska-release.pub`) and add a row to `release/README.md`. The secret key lives
only on the release owner's machine (and an offline backup). It is never in the repository,
in CI or in the build container.

The current key (`79AD6224AFF176C9`) was generated by the owner on 1 October 2026 and exists
only on his machine, passphrase-protected. A developer-generated bootstrap key
(`A50C49A866157F9`, no passphrase) signed one internal candidate the same day, was retired
within hours and all its copies were destroyed; nothing published was signed with it.
Rotation changes every embedded key, so it is a release of its own: commit the new public key,
rebuild, re-sign.

## 3. Build (anyone, reproducibly)

```sh
git checkout vX.Y.Z
RELEASE_CONTAINER=1 scripts/release.sh vX.Y.Z      # builds release/Dockerfile (Debian 13) and runs inside it
# or, on a Debian 13 machine with the pinned toolchain:
scripts/release.sh vX.Y.Z
```

The build step (a) refuses a dirty tree or a HEAD that is not the tag, (b) runs the
reproducibility gate (`REPRODUCIBLE: OK` — two clean static builds, identical hashes),
(c) packages the GUI tarball directory with the key and tag embedded, (d) copies the static
relay and writes `RELEASE-NOTES.txt`. Nothing is signed yet, and the tarball is not made yet:
`SHA256SUMS` inside it must be signed first.

Independent rebuilders run the same step **in the same container image** and compare
`dist/release/<tag>/aska-gui-…/SHA256SUMS` with the published one; all three binaries then
match byte for byte. Outside the container they will not: the static binaries link glibc in,
so the C library version is part of the bytes, and the GUI links the build machine's GTK.
(Learned at the alpha: the owner's Ubuntu 26.04 build and the developer's Ubuntu 24.04 build of
the same commit differed, as they must. `REPRODUCIBLE: OK` on one machine states determinism
on that machine; equality across machines needs the shared image.)

## 4. Sign (the release owner, on the machine with the secret key)

```sh
ASKA_RELEASE_SECKEY=~/.minisign/aska-release.key scripts/release.sh vX.Y.Z --sign
```

Signs `SHA256SUMS` inside the tarball directory (trusted comment `aska vX.Y.Z SHA256SUMS`),
makes the deterministic tarball, signs the tarball, the relay and `SHA256SUMS.txt`, verifies
every signature with the public key, and finally runs the shipped `bin/aska verify` from inside
the unpacked directory — it must print `status: MATCH` or the step fails.

## 5. Transparency (optional but intended)

```sh
scripts/release.sh vX.Y.Z --rekor      # needs rekor-cli; records the tarball signature
```

The Rekor entry (UUID/URL) is written into `RELEASE-NOTES.txt` and `REKOR.txt`. Anyone can
later check that the signature they hold is the one that was logged.

## 6. Publish and announce

Publish `dist/release/<tag>/` as it is. The announcement carries the SHA-256 of the tarball and
of `bin/aska-gui`, the key id and the Rekor entry — and the fingerprints are what members pass
on **out of band** (spoken, on paper, in a Key Card) before anyone downloads anything (§9.4).
Aska has no update check by design; "never install an update because software told you one
exists" is in every `README.txt`.

## 7. Platform gate before a non-alpha release

The M6 checklists (`docs/Aska_Platform_Validation_Checklists_M6_v0.2.md`): B (Tails 7) with
zero deviations, C and D (Qubes simple and split), and A on Debian 13, all on the signed
tarball. The alpha was cut with A run on Ubuntu 26.04 only and B/C/D open (checklist §8).

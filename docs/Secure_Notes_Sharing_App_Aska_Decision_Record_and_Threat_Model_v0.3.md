# Part I — Decision Record

## 1. Purpose

This document closes the research phase and opens the design phase. Part I records the decisions taken on 25 September 2026 that fix the shape of version 1, with the alternatives considered and the conditions under which each should be revisited, and the two decisions of 30 September 2026 (D-16, D-17) that were taken during implementation and folded in with this version. Part II states the threat model those decisions were made against: what is protected, from whom, and what is explicitly not defended. Part III turns both into numbered requirements that the coming specifications — the Block format, the Dead Drop protocol and the client — must trace to.

## 2. Summary of version 1

> **Version 1 in one paragraph**
>
> A **desktop Linux application** (Tails and Qubes as reference environments) for a **small, trusted circle under high threat**, implementing **Option C with the digital core first**. A note is sealed into a fixed-size, random-looking **Block** using a fresh 256-bit symmetric key with a key-committing AEAD; the Block is posted over **Tor to a self- or friend-hosted onion-only Dead Drop relay** that stores it under a random label until its **time-to-live expires** (default 24 h, maximum 7 days) and keeps no logs or accounts. The **key travels separately**: by default as a QR code or 24 words over a second channel (**no public-key cryptography at all**); optionally encapsulated to a **one-time hybrid post-quantum receiving key (X-Wing)** the receiver published earlier. For coercion resistance the key can be **split 2-of-3 or 3-of-5 among human trustees**, with verification, and reassembled only on the receiver's device. Every Block carries a **decoy slot** and supports a **distress passphrase**. Receivers **download the whole recent bucket** and try their keys locally, so the relay never learns who a Block is for. The client is **native, reproducibly built, amnesic**: nothing is written to disk in plaintext, keys are zeroised after use, there is no history and no identity. The **paper / one-time-pad mode** follows in a later release using the same container. Keys are never reused; there is no audit receipt; cover traffic is modest; the client warns on weak platforms; independent legal review precedes any release beyond the circle. The working name of the application is **Aska**.
>
> **Added in 0.3.** The **receiving-key path is part of version 1** (D-17, milestone M5c): a receiver creates a receiving key once, publishes the public `askar1…` Receiving Key by any channel, and the sender seals to it — nothing secret travels and there is no hand-over; the two parties confirm the key's eight-character *check* over a second channel. When the **local network blocks Tor**, Aska does not work around it: it detects the condition where it can, says so, directs the user to the platform's own Tor connection tool, and can use Tor Browser's Tor once that has connected; it never configures Tor and never falls back to a non-Tor path (D-16).

## 4. Consequences of the decisions

Taken together the decisions have some consequences worth stating plainly. Version 1 has **no server-side state beyond expiring Blocks, no accounts, and no operator role** — which means there is also no way to recover a lost key, no way to know whether a Block was collected, and no support desk that can help; for the target user these are features. The **default path contains no public-key cryptography**, so the post-quantum question reduces to "is AES/XChaCha with 256-bit keys safe", to which the 2026 answer is yes; the optional X-Wing path is where PQ hybrid cryptography enters and where agility matters most. **Expire-only disposal** means a Block may sit on a relay for up to seven days as noise; that is acceptable because the key is elsewhere and the Block is indistinguishable from decoy traffic. **Desktop first** means the mobile duress/auto-reboot story is deferred; the desktop equivalent is running from Tails or a Qubes disposable, which the client will guide. **No timelock in v1** means the solo-traveller case (Option C doc UC3) requires a human trustee; that is a deliberate trade for avoiding a trusted third party and a non-PQ component.

Two consequences follow from the decisions of 30 September 2026. **With D-17 the hybrid post-quantum path ships in version 1**, so the agility and review burden that §3 placed on "the optional path" is a v1 burden: the X-Wing composition, the `elligator2` crate and the accepted T-28 bias are named items for the external review (OPS-05), and the sender of a receiving-key Block holds nothing to hand over, so the Guarded level (Shares) does not apply to that path — the receiver's protection against coercion there is the short TTL and the fact that the seed is theirs alone. The symmetric default and its "no public-key cryptography" property are unchanged. **With D-16 a network that blocks Tor is an availability failure and nothing more**: the client has no second path, sends nothing outside Tor, and the only thing the local network learns is that Tor was attempted — which the attempt already revealed. The remedy lives in the platform (its Tor connection tool), not in Aska; on a network whose owner forbids Tor the correct response is to use another network, and the client's messages do not suggest otherwise.

# Part II — Threat Model

## 5. System context

Version 1 consists of three components and two kinds of out-of-band channel. The **Client** is a native Linux application (with a command-line core) run by senders, receivers and trustees. The **Dead Drop** is a stateless onion-service relay run by a member of the circle. The **Block** is the data format that passes between them. The **key channel** is whatever the sender and receiver use to move the key or its Shares — a QR shown in person, words read over a call, a receiving key published earlier. The **Tor network** carries Blocks between Client and Dead Drop. Nothing else exists: no directory, no account server, no update server (releases are files with published fingerprints), no analytics. On the receiving-key path (D-17) the key channel carries nothing secret: the public Receiving Key may travel over any channel, including a public one, and only its eight-character *check* needs a second channel to confirm authenticity. The Client uses the **system Tor** (or Tor Browser's Tor) through a loopback SOCKS port — or, on a detected Whonix Workstation only, the Whonix gateway address 10.152.152.10 — and never configures it (D-16).

## 6. Assets

| ID | Asset | Property to protect | Where it exists |
|---|---|---|---|
| AS-1 | Note plaintext | Confidentiality; integrity | Sender's memory while writing; receiver's memory while reading; nowhere else, ever. |
| AS-2 | Note key (and Shares) | Confidentiality; availability until read; destruction after | Sender's memory until hand-over; key channel in transit; receiver's memory; trustees' Share storage (wrapped). On the receiving-key path: the sender's memory only until sealing; never on any channel. |

## 7. Actors and trust assumptions

| Actor | Role | Trusted for | Not trusted for |
|---|---|---|---|
| Sender | Writes and posts a note; hands over key or Shares | Not retaining plaintext or key (enforced by client) | Device integrity at time of writing (see A-6) |
| Receiver | Collects and reads | Not retaining plaintext (enforced by client); not photographing the screen (guidance only) | Device integrity; resisting coercion (the design assumes they cannot) |
| Trustee | Holds one Share | Producing the Share when asked by the legitimate receiver | Confidentiality — a Share must be worthless alone; resisting coercion |
| Dead Drop operator | Runs a relay | Availability, best effort | Anything else: assumed compromised, coerced or malicious at any time |
| Tor network | Carries traffic | Hiding client IP from the relay against local observers | Resisting a global passive adversary or guard discovery over long periods; being reachable from every network (T-26) |
| App distributor / build pipeline | Produces releases | Nothing — every release must be independently verifiable | Not being coerced or compromised (EncroChat, Ghost) |
| Cryptographic libraries | Implement primitives | Correctness of formally verified / widely reviewed code | Side-channel freedom on hostile hardware |

*Table 3 — Actors and trust. Note that nobody is trusted for confidentiality except the sender and receiver themselves, and only while the note is on their screen.*

## 8. Adversaries

| ID | Adversary | Capabilities assumed | Not assumed |
|---|---|---|---|
| A-1 | Relay adversary | Full control of any Dead Drop host at any time (operator malice, seizure, compromise); sees all Blocks, all connection timing over Tor, can alter or withhold Blocks. | Seeing client IPs (onion-only); knowing any key. |
| A-2 | Local network observer | Sees a participant's ISP-level traffic: that Tor is used, when, and how much. | Breaking Tor encryption; seeing the relay side. |
| A-3 | Global passive adversary | Records traffic at both the client and relay ends; performs timing/volume correlation; may run Tor relays. | Breaking AEAD or hybrid KEM; active manipulation at scale (partially covered by A-1). |
| A-4 | Forensic examiner | Physical possession of a participant's device, locked or unlocked, with commercial extraction tooling; disk imaging; RAM capture if powered. | Breaking full-disk encryption of a powered-off device with a strong passphrase. |
| A-5 | Coercer (legal or physical) | Can compel any *one* participant at a time to do anything they are able to do: produce keys, enter passphrases, run the client, call a trustee. Includes courts (RIPA-style notices) and violence. | Compelling ≥ k participants simultaneously; knowing in advance which passphrase is real (decoys). |
| A-6 | Endpoint malware | Full control of a participant's device while the client runs: screen, keyboard, memory. | Nothing — this adversary wins against the note on that device; the goal is blast-radius limitation. |
| A-7 | Supply-chain adversary | Can attempt to substitute the client binary or a dependency, or poison an update. | Forging signatures / breaking the transparency log; compromising every independent rebuilder. |
| A-8 | Future quantum adversary | Has recorded all traffic and all Blocks today; in ~2035 has a cryptographically relevant quantum computer (Shor against RSA/ECC; Grover against symmetric). | Breaking 256-bit symmetric or information-theoretic schemes. |
| A-9 | On-path censor (DC-01) | A network operator or national censor between the client and the Tor network who blocks connections to Tor relays (and, in an arms race the Tor Project runs, to known bridges). Overlaps A-2 in position and capability, but the goal is denial rather than observation. | Observing more than A-2 does; breaking Tor; reaching the relay side. |

*Table 4 — Adversary model. A-5 and A-6 are where designs usually fail; the model limits what they gain rather than pretending to stop them. A-9 added in 0.3.*

| ID | Threat | Adversary | Mitigation in v1 | Residual |
|---|---|---|---|---|

| T-17 | Malware on sender or receiver device | A-6 | Blast radius: no archive, no contacts, no identity, no signatures, no reusable keys; per-Block keys; guidance to hardened platforms. | Current note exposed — accepted. |
| T-18 | Poisoned client release or dependency | A-7 | Reproducible builds; Sigstore-signed, transparency-logged releases; fingerprint shown in client; no auto-update; minimal, pinned, verified dependencies. | User who never verifies. |
| T-19 | Web/JS delivery of the client | A-7 | There is no web client. CLI + native GUI only. | None. |
| T-20 | Quantum decryption of recorded Blocks | A-8 | Default path symmetric-only (Grover-resistant at 256 bits); optional path hybrid X-Wing (ML-KEM component quantum-resistant), built in v1 (D-17); Shamir unconditional. | None known. |

| T-22 | Cryptographic break of a chosen primitive | any | Versioned format inside the envelope; agility; libraries with verification; two independent layers where a passphrase is also used. | Format bump required. |

| T-25 | Stylometric attribution of note text | A-1/A-3 after compromise | Out of scope for v1; optional style-neutralising guidance later. | Accepted. |
| T-26 | The local network blocks Tor: the client cannot reach any Tor relay; no Block can be posted or fetched (DC-01) | A-9 (overlaps A-2) | D-16: detection with the platform's bridge tool named (option A) — with a control port, bootstrap below 100 % is reported as a warning naming the tool; without one, the same direction is given when every attempt of an operation fails with the blocked-network signature; Tor Browser's Tor usable via `--tor-browser`; session-scoped bridges via the control port in v1.1 (option B); the client never falls back to a clearnet path. | T-27 | Substituted Receiving Key: the sender encapsulates to the adversary's key; the adversary reads the note, and can re-seal it to the real key to hide the substitution (DC-02) | Anyone who can alter the channel over which the public Receiving Key travels — an active A-2, a compromised website or messenger account | The eight-character check, confirmed over a second channel before the first note; the client shows it prominently on both sides (KEY-09; the sender's client prints the check of the key it sealed for). A receiving key published in several places (site, profile, signed message) is harder to substitute everywhere. Impact is the confidentiality of that note — the same class as giving someone a wrong phone number for the voice hand-over. **Seed compromise (KEY-07 applied):** a leaked receiving seed opens every Block encapsulated to it that is still on a relay or was captured; mitigation: one key per note (the client says so after each open), short TTLs, and the seed never written by the client. | A sender who skips the check has no protection against substitution — as on the symmetric path a sender who reads the words over the wrong channel has none. |
| T-28 | KEM-region distinguishability: statistical estimate of how many Blocks in a bucket carry an ML-KEM ciphertext, from the small bias that ML-KEM ciphertext compression with q = 3329 introduces (DC-02) | A-1, or anyone who copies buckets (A-3) | Elligator2 encoding of the X25519 half (KEY-12) removes the decisive tell; ML-KEM ciphertexts are pseudorandom under MLWE (Maram & Xagawa, PKC 2023) up to the compression bias, which is small and needs many samples. With one Block an observer cannot tell a KEM-path Block from a random-fill one; with a large sample from one relay a test could in principle estimate the *fraction* that carry ML-KEM ciphertexts — never which ones. Impact: reveals that the KEM path is in use on this relay; reveals nothing about any single Block, sender or receiver. | **Accepted for v1**; review item for the external review (OPS-05): the sample size at which the bias becomes measurable on a real relay. |

## 10. Explicitly out of scope for version 1

- Protecting a note from a device that is compromised while the note is being written or read (T-09, T-17). The design limits consequences; it does not prevent them.
- Resistance to a global passive adversary performing end-to-end traffic correlation (T-06). Mitigated, not solved; a mixnet transport is a roadmap item.
- Availability guarantees. A relay may be offline; senders may post to two relays; there is no delivery confirmation by design.
- Group messaging, threads, attachments larger than the largest Block class, or any form of conversation history.
- Mobile clients, timelock Shares, threshold decryption, anamorphic encryption and the paper/one-time-pad mode — all roadmap, all designed for in the Block format. (The receiving-key path, deferred to v1.1 at specification level by S-04, is **in** scope since D-17.)
- Legal protection for the *act* of using the system, possessing it, or triggering the distress function; addressed by D-13.
- **Working around a network that blocks Tor (D-16, DC-01 §9).** Aska's guidance addresses networks that censor Tor — the environment its users are designed for, and a standard, documented Tor use case. The client does not acquire bridges, does not probe or fingerprint the network it is on, and does not attempt to defeat any particular network's policy. On a network whose owner forbids Tor, such as an employer's, the correct response is to use another network; the client's messages do not suggest otherwise. Session-scoped bridge configuration through the control port, with bridge lines the user obtained through Tor's own distribution channels (option B), is v1.1 and does not change this boundary.
- Enforcing single use of a receiving seed. The format cannot enforce it and the client does not (KEY-07 as revised): the client tells the receiver after each open and the choice is theirs.

# Part III — Requirements

Requirements use MUST / SHOULD / MAY in the RFC 2119 sense (SHALL = MUST in the requirements imported verbatim from DC-01 and DC-02). Each cites its source decision (D-nn) and the threats (T-nn) it addresses. "Client" means the desktop application and its command-line core; "Relay" means the Dead Drop software.

## 11. Block format (BLK)

| ID | Requirement | Trace |
|---|---|---|
| BLK-01 | A Block MUST be indistinguishable from uniformly random bytes to anyone without a valid key: no plaintext header, magic bytes, version field, length field or checksum in the clear. | D-07, D-14; T-04, T-16 |
| BLK-02 | Blocks MUST belong to one of a small fixed set of size classes (proposed: 4 KiB, 16 KiB, 64 KiB); a note MUST be padded with random bytes to its class boundary. | D-05; T-04 |
| BLK-03 | Each Block MUST be encrypted under a fresh, uniformly random 256-bit note key generated from the operating system CSPRNG mixed with a second independent entropy source where available. Keys MUST never be reused across Blocks. | D-08, D-14; T-01, T-20 |
| BLK-04 | The AEAD MUST be XChaCha20-Poly1305 with a 192-bit random nonce, wrapped in an explicit key-commitment construction so that no ciphertext decrypts validly under two different keys. | D-14; T-24 |
| BLK-05 | A Block MUST contain at least two logical slots (real note and decoy), each opened by an independent passphrase-derived or directly supplied key; the number of occupied slots MUST NOT be determinable without a key. Unused slot space MUST be random filler. | D-07; T-12, T-16 |
| BLK-06 | A versioned format identifier and algorithm identifiers MUST exist *inside* the authenticated encrypted envelope, never in the clear, to allow future algorithm changes. | D-14; T-22 |
| BLK-07 | When the optional receiving-key path is used, the note key MUST be encapsulated with X-Wing (X25519 + ML-KEM-768) to a one-time receiving key; the encapsulation ciphertext MUST be placed inside the size class such that BLK-01 still holds (e.g. by a random-looking encoding). *Status (0.3):* built in v1 (D-17, M5c); the random-looking encoding is KEY-12; Block Format §4.2, §6.5. | D-04a, D-17; T-20, T-22, T-28 |
| BLK-08 | The Block MUST NOT contain any sender or receiver identifier, timestamp, device identifier or signature. Authentication is implicit via the AEAD and, on the receiving-key path, via KEM-derived MAC only. | D-09; T-02, T-11, T-15 |
| BLK-09 | A Block label (relay storage key) MUST be 256 bits, uniformly random, generated by the sender, and computationally independent of every key — derivable only by a holder of the root R. *Refined in 0.3 per Block Format §11:* v0.2 said "unrelated to the note key"; the specification derives the label one-way from R so that a receiver can match its Block locally in a bucket without any per-Block request to the relay (RLY-02) and so that Shares need not carry the label (KEY-03). The label reveals nothing about R or any key; the intent — the relay cannot learn anything about the key from the label — is preserved. | D-05; T-02, T-23 |
| BLK-10 | The format MUST be specified precisely enough (byte layout, KDF parameters, test vectors) that an independent implementation can interoperate — this is the deliverable *Block Format Specification v0.1*. | D-02 |

**Specification-level decision S-04 (revised by D-17).** Block Format draft 0.2 decided S-04 as "X-Wing KEM path deferred to v1.1; v1 clients are symmetric-only and fill the KEM region with random bytes", with two prerequisites (Elligator2 access in the X-Wing implementation; confirmation of ML-KEM ciphertext pseudorandomness under compression). On 30 September 2026 D-17 revised it to: "KEM path as in DC-02 §2, built in v1 (M5c); version-1 clients that do not implement it fill the KEM region with random bytes (unchanged); implementations that do MUST follow DC-02 §2.2 (Block Format §6.5.2) for the X25519 half. No change to the Block layout." Block Format draft 0.4 §6.5 and §7.5 are the normative text.
